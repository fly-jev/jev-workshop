Workshop · modelos de decisão

Onde o agente decide, e por que isso não precisa ser um LLM

Um agente passa a maior parte do tempo decidindo, não escrevendo: qual caminho seguir, qual ferramenta usar, se a resposta está boa, se precisa de um humano. Cada uma dessas decisões é uma pergunta de opções fechadas. É aí que entra um modelo de decisão.

1 · O que é um agente

Um agente é uma corrente de decisões e ações

Jogar a mensagem direto num LLM, mesmo com memória e tool calling, raramente basta. Na prática, antes e depois de o LLM escrever, alguém precisa decidir o que foi pedido, quem responde, se precisa de RAG ou de uma ferramenta, e se a resposta pode sair.

Como parece

mensagem do usuário
LLM + memória + tools
resposta

Como funciona bem

mensagem do usuário
◆ o que foi pedido?
◆ quem responde? modelo leve, forte ou humano
◆ precisa de RAG ou de qual tool?
⚙ executa a busca / a tool
✎ LLM escreve a resposta
◆ a resposta está boa? pode sair?

Os ◆ são a maior parte do fluxo. O fluxo completo, passo a passo, está na seção 5.

2 · Como se decide

Do if ao modelo de decisão

AbordagemO que exigeOnde dói
Regras (if, threshold)escrever cada regranão entende linguagem natural; as regras se multiplicam
Modelos clássicos (regressão, árvores)features e dados rotuladostreinar, monitorar drift, re-treinar
Redes neurais, BERT treinadomilhares de exemplos rotulados, GPU para treinaridem, e uma nova categoria pede novo treino
LLM / VLM com Pydanticsó escrever a perguntacaro e lento: 2,6 a 4,3 s e ~US$ 0,0018 por decisão
Modelo de decisãosó escrever a pergunta~100 ms de processamento e ~US$ 0,000012, com probabilidade

Até o BERT, cada decisão nova é um projeto de dados: rotular, treinar e manter o modelo respondendo bem. O LLM tirou o treino do caminho, mas cobrou em dinheiro e tempo. O modelo de decisão mantém a praticidade do LLM com custo e latência de modelo pequeno.

Se existe modelo aberto, até BERT-like, vale pagar uma API? Quase sempre, sim. Em produção, o volume raramente enche a GPU (ou a CPU, no caso do BERT) a ponto de compensar manter a máquina: paga-se pelo tempo ocioso e pela operação. Quem já chama OpenAI ou Anthropic por API não troca isso por servidor próprio para economizar centavos.

Quanto custa a mesma decisão

Mesmo payload: ~400 tokens de entrada. Os LLMs pensam (reasoning) e devolvem o JSON tipado: ~400 tokens de saída (~330 de raciocínio + ~70 de JSON). O modelo de decisão não gera texto.

4 · Ponto de partida

Três jeitos de um agente decidir

A mesma mensagem, "Bom dia! Tudo bem?", passando por três arquiteturas. Todas respondem bem; o que muda é quanto custa, quanto demora e o quanto você enxerga e controla cada decisão.

Jeito 1 · o mais comum

Tudo no LLM forte

mensagem
LLM forte + ferramentas
decide tudo por dentro e escreve
resposta
  • Simples de montar.
  • Paga o modelo grande até para um "bom dia".
  • As decisões ficam escondidas na geração: não dá para medir nem ajustar "escalar?" separadamente.
Onde a maioria está.
Jeito 2 · a boa prática hoje

Uma chamada ao LLM com Pydantic por decisão

mensagem
LLM → Route(path=...)
JSON validado
modelo leve escreve
  • A decisão é explícita, testável e validada.
  • Mas cada decisão é uma geração inteira: segundos e tokens de saída.
  • Devolve um rótulo, sem grau de certeza.
Medido: 2,6 a 4,3 s · ~US$ 0,0018 por decisão.
Jeito 3 · o próximo passo

Modelo de decisão

mensagem
fly-jev → p(modelo_leve) = 0,98
uma probabilidade por opção
modelo leve escreve
  • A mesma decisão explícita do jeito 2.
  • Em centenas de milissegundos, por uma fração do custo.
  • Com probabilidade: a aplicação sabe quando está em dúvida.
Medido: ~90–150 ms de processamento · ~US$ 0,000012 por decisão.

Medições do roteamento da seção 7, 26/10/2026, uma rodada por mensagem. O jeito 1 descreve agentes em que o LLM conduz o próprio uso de ferramentas; o jeito 2 é o padrão "routing" de Building effective agents (Anthropic).

Cada ◆ nos jeitos 1, 2 e 3

No jeito 1, nenhum ◆ existe como passo separado: o LLM forte decide tudo dentro da geração. Nos jeitos 2 e 3, cada ◆ vira uma chamada explícita:

Jeito 2: cada ◆ é uma chamada ao LLM

Um prompt pedindo JSON, validado com Pydantic. Funciona, mas cada decisão custa uma geração inteira: segundos de latência e tokens de saída. A resposta é um bool ou uma str, sem grau de certeza.

Jeito 3: cada ◆ é uma pergunta ao modelo de decisão

Estado + pergunta + opções → uma probabilidade por opção, em centenas de milissegundos. A aplicação decide o que fazer com a incerteza: seguir, pedir mais informação ou chamar um humano.

O modelo de decisão não substitui o agente. Ele tira das costas do LLM as decisões intermediárias e deixa para o LLM o que só ele faz: escrever.

6 · Conceito

Como um modelo de decisão funciona

Você manda três coisas, e recebe probabilidades:

EntradaO que éNo fly-jev
EstadoO contexto: a mensagem, a política da casa, o histórico, as imagens.state (texto ou JSON) e images
PerguntaO que precisa ser decidido, escrito como para uma pessoa nova no time.instructions
OpçõesAs respostas possíveis, com uma descrição quando o nome sozinho é ambíguo.criteria

Há três tipos de pergunta: choice (uma entre várias opções), noul (sim ou não, devolve p(sim)) e score (nível numa escala). Não há texto livre na resposta: ela é sempre uma das opções que você definiu.

POST https://br.fly-jev.com/v1/decisions
{
  "model": "fly-jev-y0-lite",
  "state": "Cliente reclamou que o pedido não chegou.",
  "questions": {
    "time": { "type": "choice", "instructions": "Qual time deve atender?",
              "criteria": { "entrega": null, "pagamentos": null, "outro": null } }
  }
}
→ "answers": { "time": { "choice": "entrega",
                         "probabilities": { "entrega": 0.91, "pagamentos": 0.06, "outro": 0.03 } } }

Exemplo de resposta e tipos de pergunta: fly-jev · Como usar e Tipos de decisão. Modelos: fly-jev-y0-lite (só texto) e fly-jev-y0 (texto + até 4 imagens).

A qualidade depende do enunciado O mesmo modelo, com a mesma entrada, dá respostas diferentes quando a pergunta muda. Se a regra da casa não está escrita no estado ou na pergunta, nenhum modelo vai adivinhá-la. Ver fly-jev · Enunciado curto e completo.

7 · Caso 1 · Roteamento

Roteamento: "Bom dia! Tudo bem?" não precisa do modelo mais caro

É o passo ◆1 do fluxo. Uma única pergunta choice decide o caminho da mensagem. Uma saudação vai para um modelo leve (por exemplo, google/gemini-3.8-flash); uma pergunta sobre regras passa pelo RAG; um pedido de cálculo vai para um modelo com reasoning; uma ameaça jurídica vai para um humano.

"questions": { "rota": {
  "type": "choice",
  "instructions": "Qual caminho o agente deve usar para responder esta mensagem?",
  "criteria": {
    "modelo_leve": "saudação, agradecimento ou conversa simples, sem consultar dados",
    "rag":         "pergunta sobre regras, prazos, preços ou informações que estão na base de conhecimento",
    "reasoning":   "pedido que exige comparar opções, calcular ou planejar em vários passos",
    "humano":      "reclamação grave, ameaça jurídica, fraude ou pedido explícito por um atendente"
  }
}}

No jeito 2, a mesma pergunta e as mesmas opções vão para o LLM, e o Pydantic garante que a resposta é uma das quatro:

class Route(BaseModel):
    path: Literal["modelo_leve", "rag", "reasoning", "humano"]   # vira um enum no JSON Schema
    reason: str

O que observar: os dois acertam as quatro. A diferença é que o jeito 3 custa ~150× menos e informa a certeza; com ela, a aplicação pode mandar para o modelo forte quando nenhuma rota está claramente na frente (o slider "trust route" do app).

Experimente Na aba Routing do app, escreva mensagens que fiquem entre duas opções ("Oi, qual o valor da mensalidade?" é saudação ou RAG?) e veja a probabilidade se dividir. Depois melhore a descrição das opções até a decisão ficar clara. Remova as descrições (null) e compare.

8 · Caso 2 · Texto

A blusa: a mesma mensagem, duas decisões

É o passo ◆5 do fluxo. Mensagem do cliente: "Você tem a blusa cod 123 na cor preta?" Pergunta: "Esta mensagem precisa ser transferida para um atendente humano?" (noul). A única coisa que muda é a política. Exemplo do playground do fly-jev.

A política vai antes da mensagem

A política é igual em todas as chamadas; a mensagem muda a cada uma. Colocando o trecho fixo primeiro, o provedor reaproveita o cache do prefixo e só processa o que é novo.

state = "{política}\n\nMensagem do cliente: {mensagem}"     ← fly-jev (app/escalation_jev.py)
system = "{política}\n\n{pergunta}" · user = "{mensagem}"   ← LLM     (app/escalation_llm.py)
Política no início do estadofly-jev p(sim)LLM (JSON tipado)
(nenhuma)0,72 → transferirneeds_human: false → automatizar
"Considerando que o agente automático tem acesso às ferramentas de consulta de estoque e de entrega."0,003 → automatizarneeds_human: false → automatizar

Medido neste app em 26/10/2026, uma rodada. LLM: anthropic/claude-sonnet-5.5 via Hecate.

O que observar: sem política, o modelo de decisão responde à pergunta literal ("um humano deveria ver isso?") e transfere. O LLM automatiza mesmo sem política, porque supõe que pode consultar o estoque; a justificativa dele diz isso. Ele preencheu uma regra que ninguém escreveu. Com a política explícita, os dois concordam.

Experimente (aba Text do app) Escreva uma política de escalonamento ("só escalamos em fraude, ameaça jurídica ou risco à saúde") e teste mensagens como "Quero trocar o tamanho" e "Vou processar vocês". Depois escreva a mesma política de forma exagerada ("automatizamos tudo") e veja o modelo parar de escalar casos graves.

9 · Caso 3 · Imagem

Tem assinatura?

Uma decisão multimodal: o estado inclui a imagem do documento (fly-jev-y0). Pergunta, igual nos dois caminhos: "Does this document have a signature?"

Medido neste app em 26/10/2026, duas rodadas por documento. Custos de usage.cost_usd (fly-jev) e usage.cost (Hecate). A maior parte da latência do fly-jev é rede e envio da imagem; mande JPEG em vez de PNG.

O que observar: nos dois primeiros documentos os dois acertam; a diferença é custo e latência. No contrato eles discordam, e nenhum está "errado": um nome digitado em fonte cursiva é assinatura? Depende da regra da casa. Se a regra é "assinatura de próprio punho", ela precisa estar no enunciado.

Experimente (aba Image do app) Mude a pergunta em app/signature_jev.py e app/signature_llm.py para "assinatura de próprio punho, não nome digitado" e rode o contrato de novo. Traga fotos de documentos reais tiradas com o celular, com sombra e ângulo.

10 · Política da aplicação

De probabilidade para ação

O modelo dá a probabilidade; a aplicação decide o que fazer. Essa regra mora em código (app/policy.py), não no prompt:

def decide_from_jev(p_signed, accept_above=0.8, reject_below=0.3):
    if p_signed >= accept_above: return "accept"
    if p_signed <= reject_below: return "ask_resubmit"
    return "human_review"          # a zona de dúvida vira revisão humana

Com um booleano

Só existem duas saídas. Um caso duvidoso é aceito ou rejeitado com a mesma convicção de um caso óbvio.

Com uma probabilidade

Os cortes são uma escolha do negócio: mais altos quando um falso positivo custa caro. Mudar o corte não exige chamar o modelo de novo, como mostram os sliders no app.

Rodar na sua máquina Precisa só de Git e Docker. Código em github.com/fly-jev/jev-workshop. 
git clone https://github.com/fly-jev/jev-workshop.git
cd jev-workshop
cp .env.example .env      # preencha LLM_API_KEY e JEV_API_KEY
docker compose up
Abra http://localhost:8000. Sem as chaves, o app roda em modo simulado (respostas por heurística, sem custo nem latência reais). Se a porta 8000 estiver ocupada, use APP_PORT=8088 docker compose up e abra a 8088.

Três mensagens

  1. Nem toda decisão precisa de um LLM generativo.
  2. A qualidade depende da pergunta, do contexto e das alternativas.
  3. O modelo fornece probabilidades; a aplicação define como agir.
